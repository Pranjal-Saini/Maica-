# Deploying

Two paths are configured. **Render is the recommended one** and is what
`docs/tech-stack.md` already names; Vercel works but costs the product two
things it depends on.

## Render (recommended)

The repo carries a `render.yaml` blueprint. Render → **New → Blueprint** →
pick this repo. It creates the web service and its Postgres together, builds
the existing `Dockerfile`, and runs `alembic upgrade head` before the new
instance takes traffic.

Three secrets are marked `sync: false` and must be set in the dashboard:

| Variable | Value |
|---|---|
| `GOOGLE_CLIENT_ID` | from the Google Cloud console |
| `GOOGLE_CLIENT_SECRET` | from the Google Cloud console |
| `GOOGLE_REDIRECT_URI` | `https://<service>.onrender.com/auth/google/callback` |

That same redirect URI must also be registered as an **Authorised redirect
URI** on the OAuth client in the Google Cloud console, or sign-in fails with
`redirect_uri_mismatch`.

`SESSION_SECRET_KEY` is generated by Render on first deploy. Do not rotate it
casually — it signs session cookies, so a new value signs every user out.
`ENVIRONMENT` is set to `production` in the blueprint, which is what turns on
the `Secure` cookie flag, HSTS, and the refusal to boot on the published
development session key.

### If the deploy exits before binding

Two failures look like "no open ports detected" but are not port problems:

- `SESSION_SECRET_KEY is still the development default` — the app refuses to
  start rather than sign cookies with a value published in `.env.example`. Set
  the variable; the process never reached the point of opening a port.
- Any other startup exception. The port scan message is always the *symptom*;
  read the lines above it.

The container binds `$PORT` when the host sets one (Render defaults to 10000)
and 8000 otherwise, so no port configuration is needed on either side.

### Sizing

The web service is `1c-2g` rather than the cheaper 512 MB plan because parsing
a 25 MB upload peaks at roughly 494 MB of heap before any ORM object exists.
A 512 MB instance would OOM on a file inside the app's own stated limit.

The database is the smallest paid plan rather than `free`, because Render
deletes a free Postgres after 30 days and this one holds client evidence.

## Vercel

`pyproject.toml` declares `[tool.vercel] entrypoint = "maica.api.main:app"`.
Without it the FastAPI preset builds cleanly and every route returns 404 —
Vercel only scans for `app.py`, `index.py`, `main.py`, `server.py`, `wsgi.py`
or `asgi.py` at the repo root or in `src/` or `app/`.

Set the same environment variables as above, plus `DATABASE_URL` from a
managed Postgres (Neon or Supabase via the Vercel Marketplace — Vercel does not
host one), and run `alembic upgrade head` against it yourself; there is no
pre-deploy hook.

**Two limits to accept before choosing this:**

- **Uploads are capped at 4.5 MB**, not the app's 25 MB. Vercel rejects a
  larger request body with `FUNCTION_PAYLOAD_TOO_LARGE` before any application
  code runs. Path A — the consultant uploads the export they already have — is
  the wedge, and real System Notes exports exceed 4.5 MB routinely.
- **No Ollama.** `ollama_base_url` points at `localhost:11434`. Nothing serves
  that inside a Vercel function, so every LLM explanation fails. Reports still
  render — the ranked factors and their evidence are computed deterministically
  — but they carry no generated narration until a hosted model sits behind the
  `LLMClient` protocol.

Function duration (300 s on Hobby) and memory (2 GB) are both fine; the
180 s LLM timeout and the 494 MB upload peak fit inside them.

## Either way

`GOOGLE_REDIRECT_URI` changes per environment and is the single most common
first-deploy failure. Check it before anything else when sign-in breaks.
